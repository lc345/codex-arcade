# Agent Stage: 1,000 款精品小游戏制作计划

状态: 历史长期路线图，不是当前发布清单。当前版本共 100 款，原来的 26 款已退役，详见 [现有游戏清单](PLAYABLE_INVENTORY.zh-CN.md)。以下完整平台能力并非全部已实现。

调研日期: 2026-09-17。数量、性能、包体和试玩门槛均为本项目的规划目标，不是 Steam 标准，也不是已经达到的指标。

## 1. 总体决策

把长期目标从“一万个作品”收敛为“一千个经过筛选、独立可玩的精品小游戏”。建议使用 **20 个制作大类、100 个玩法方向、每方向 10 个作品** 的目录结构。100 个方向需要在后续原型阶段验证，当前不声称已经找到 100 个成立且互不重复的方向。

数量包含现有 10 款，现有作品仍须通过新质量标准，不是额外再做 1,000 款。先建立可重复的制作和验收流程，再按累计 20、100、300、1,000 款推进。任何阶段都可以淘汰不成立的作品，不能为了凑满配额发布。

产品承诺: Agent 工作时，用户可以立即进入一个有明确操作、真实反馈和独特视觉的游戏；Agent 完成时，游戏立刻停下。所有创意围绕这件事展开，不重新引入等待进度表演、长剧情或确认按钮。

规划时基线是 0.6.0 的 10 款集合；首批实施已升级到 0.7.0 的 20 款、63 关与按需加载宿主。引擎对照基准、通用持久化检查点、第三方代码沙箱和远程分发继续作为后续里程碑，不能以试验版替代这些验收。

## 2. 产品边界

- 主战场是 Codex 小窗口和独立浏览器试玩页，以 2D / 2.5D 为主。不把完整商业大作缩成一个难操作的小窗。
- 不预测 Agent 还要运行多久。每款游戏在短时间内就有有效选择，更长任务则自然延伸，而不是要求用户等到一局结束。
- 任务结束立即关闭输入、物理更新、动画调度、声音和硬件反馈。不得为了结算、胜利动画或存档而推迟停止。
- 持续维护有大小上限的本地检查点；停止后可保存最后一致状态。用户下次可主动续玩，不默认偷跑未完成的一局。
- 主操作优先鼠标、触控或一两个按键。把 `one-button`、`pointer`、`keyboard` 作为能力标签，不强迫每款游戏都塞进一个按钮。
- 首期不做联网对战、MMO、长篇 RPG、写实重型 3D、需要长教程的复杂模拟器。卡牌与骰子不涉及真钱或付费抽取。
- 游戏不访问 prompt、思维过程、工具参数、源码、文件路径、原始输出。不得把游戏分数解释成 Agent 进度或工作质量。
- 静音默认开启，减少动效、键盘路径、明确焦点、色觉辅助必须保留。被折叠或切到后台时暂停。
- 成功不以用户被留住更久为标准。目标是等待更愉快，同时让用户及时回到任务结果。

### 什么算一个作品

一个作品必须有独立可玩的目标、内容组合、美术和声音表达，且能说明与同方向其他作品的实际差异。换背景、改颜色、调速度、增加一关，不算新作品。

建立玩法特征表: 主操作、状态变化、目标、失败条件、资源约束、空间结构、时间压力、策略选择。先去掉题材词再比较，防止不同名字掩盖同一玩法。

同方向的十款不是十次机械复制。进入新作品名单时，至少在目标、规则组合、关卡结构、风险回报中的两项形成可试玩的区别；是否足够不同由实际试玩判断，不由文案自评决定。十款是配额，不是自动发行资格。

## 4. “精致并有创意”的验收方式

精致不等于更复杂、更贵或更多粒子。作品要同时过以下门槛，不能用一张好看的截图抵消糟糕操作。

| 维度 | 必须交付的证据 | 不接受的情况 |
| --- | --- | --- |
| 玩法成立 | 可解释的选择、失败和改进；完整操作回放 | 自动播放、无脑连点最优、只按一下就加分 |
| 有辨识度 | 和同类的机制比较，独立视觉基调 | 同规则换皮冒充新游戏 |
| 视觉清晰 | 小窗截图、动作关键帧、最忙状态录像 | 主体被背景淹没、判定范围与画面严重不符 |
| 操作手感 | 输入到反馈测试、真实触控/键盘试玩 | 延迟、误触、镜头跟不上、点击穿透 |
| 声音完成度 | 关键事件音效映射、试听、静音替代反馈 | 每个事件同一提示音、音量失控、结束后还响 |
| 稳定与可信 | 停止、存档、性能、安全和版权检查 | 游戏影响 Agent，资源来源不明，崩溃或泄漏 |

质量方向:

- 进入后很快看到可操作对象；首个有效动作有清楚反馈，而不是先读一页说明。
- 有技能、判断或策略成长，失败能看懂原因；关卡差异不只是越来越快。
- 每款有一个可以被用户说出来的亮点，不强迫所有作品都夸张或炫光。
- 首次试玩目标: 在小规模新手组里，大多数人能在约 10 秒内理解主操作并在约 30 秒内做出有效选择。正式门槛用首批样本校准，不把小样本当统计结论。
- 正式入库前安排独立试玩，不使用作者自己的“好玩评分”证明有趣。记录看不懂的瞬间、误操作、主动重试原因和不喜欢的原因。
- 自动代理用于找漏洞、检查通关与策略退化；不能冒充真实用户对美术、乐趣和惊喜的评价。

每款至少走一次独立试玩流程。若以三位试玩者每款五分钟计算，一千款仅首轮试玩就是约 250 人时，返工复测另计。这是必须纳入计划的质量工作，不能靠增加生成 token 替代。

## 5. 视觉、动作与声音生产线

### 5.1 美术不是只画背景

每款先形成一张风格基准页: 主体轮廓、材质、光线、危险/奖励色、镜头尺度、动作气质。背景、角色、道具、机关、粒子、HUD 和声音来自同一方向。

候选风格族可包括纸艺机关、手绘童话、黏土玩具、明亮科幻、复古丝网印刷、微缩机械、陶瓷玻璃、原创像素。这里是美术组织方式，不增加游戏类别或作品数量。最终以六款标杆验证，避免一千款都变成同一种发光圆球。

对于有角色的游戏，按实际规则制作待机、移动、起手、有效动作、恢复、受击和结果状态；无角色游戏则把同样的表达投入材料、机关和环境反应。不是每款机械添加一整套无用动作。

### 5.2 三条动作制作路径

1. **精灵帧动画:** 先批准一个角色基准，再生成或绘制同一动作的整组帧，统一尺寸、锚点和方向，逐帧与连播检查。适合像素、手绘和夸张卡通。整组生成也可能出现比例漂移，必须返修，不能把 AI 输出直接当成已完成资产。可借鉴 [Game Studio sprite-pipeline](https://github.com/openai/plugins/blob/main/plugins/game-studio/skills/sprite-pipeline/SKILL.md)。
2. **骨骼/分层动画:** 分离躯干、关节、道具或机械部件，用状态驱动姿态，适合重复动作多的角色和机关。首期可用引擎变换与 Blender；Spine/Rive 作为专项工具，先审核授权、制作方式和运行时成本。
3. **3D 制作、2D 播放:** 在 Blender 建原创微缩模型，统一材质、灯光、视角和动作后渲染精灵图集。这样可获得稳定的 2.5D 体积感，用户端不必同时运行重型 3D 场景。[Blender 动画与绑定](https://www.blender.org/features/animation/)

动作反馈遵守“准备、作用、恢复”的节奏。渲染形变与权威碰撞尽量分开，不能为了夸张拉伸把判定悄悄移动。屏幕震动、拖尾、短暂停顿仅用于有意义的事件，并能降低强度。

### 5.3 声音制作

声音按事件制作，而不是随机播放背景音乐: 蓄力、移动、材料碰撞、危险接近、技能、目标达成和失败应有区分。规定并发声部、音量、冷却和优先级，避免连续碰撞叠到刺耳。

基础反馈使用现有 Web Audio；需要节奏调度的品类再使用已有 Tone.js。原创合成音效、自己录制的素材与许可明确的音效包可以组合。FFmpeg 做格式、时长、峰值和导出检查，Audacity 可用于人工听感修整。[Tone.js](https://tonejs.github.io/)、[Audacity Macros](https://manual.audacityteam.org/man/macros.html)

静音时目标、危险和结果仍可读；任务停止先静音，再处理检查点。禁止把一段生成视频当作需要响应输入的核心动画。

## 6. 技术栈决策

### 建议主线

**新增标准 2D 作品优先评估 Phaser + TypeScript，复杂刚体使用 Matter，格子/卡牌规则使用独立纯数据逻辑。现有 Canvas + Matter 十款保持可运行。**

原因不是 Phaser 会自动做出好游戏，而是它已经提供场景、精灵动画、镜头、输入、地图、资源与物理集成，更适合多个传统游戏品类持续生产。这样不用为一千款分别维护一套相似的摄像机和资源生命周期。[Phaser 官方说明](https://docs.phaser.io/phaser/getting-started/what-is-phaser)、[动画](https://docs.phaser.io/phaser/concepts/animations)、[Matter 集成](https://docs.phaser.io/phaser/concepts/physics/matter)

这是进入 P0 的推荐选型，不是本次直接迁移承诺。P0 用同一个具有动画、碰撞、镜头和声音的短场景，对比 Phaser 与现有 Canvas/Matter 基线，并评估已有依赖和 Skills 支持的 PixiJS/Matter 备选路径。测试包体、作者工作量、小窗表现、暂停和停止、CSP 兼容，通过后冻结版本；Phaser 不过线则评估备选，不影响现有十款运行。新作品只保留一条主生产线，不让社区默认维护两套不同框架。

| 工具 | 定位 | 当前态度 |
| --- | --- | --- |
| Phaser / TypeScript | 新增 2D 作品的主引擎候选 | P0 基准测试通过后采用；不要混用不同大版本 API |
| 当前 Canvas / Matter | 现有十款、简单物理模型和回归基线 | 保留，通过统一宿主适配器接入 |
| PixiJS | 高质量 2D 渲染、特殊视觉与主线备选 | 本机已有 Skills，项目已有依赖，不重复造渲染器 |
| Three.js | 少数确实受益于实时 3D 的作品 | 100 款之后再按性能验证引入，不默认加载 |
| Godot | 可视化创作和第三方贡献候选 | 不作为首期必需引擎，先验证 Web 导出体积和宿主兼容 |
| Unity / Unreal | 重型完整项目 | 当前目标不需要，暂不安装 |

Godot 有 Web 导出，但线程、浏览器和导出模式会带来不同限制，不能直接推断能无成本嵌入 Codex。[Godot Web 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

原型中成熟玩法的关键规则尽量使用适配的成熟库。不能因为换了渲染器就重新手写不稳定的刚体、碰撞或经典棋类规则引擎。

## 9. 素材与许可

- 正式作品优先原创素材；复用的是经过设计的美术系统和技术，不是把同一张背景换颜色。
- Kenney 可用作原型、基础道具、输入图标和适合的音效来源。其资产页面声明 CC0，仍应保留下载包中的来源与许可文件。[Kenney 使用说明](https://kenney.nl/support)
- 免费下载不等于允许在开源素材库中再分发。第三方音频、字体、模型逐项审核，来源不清即不发布。
- 生成素材记录工具、日期、参考来源、版本与编辑过程，不承诺独占版权，不使用未经许可的角色、商标、真人肖像或商业游戏素材。
- 代码许可和素材许可分开。不能把第三方编辑器、商业字体、模型权重或受限素材打进开源安装包。
- 成品图集与原始创作文件分开管理。需要时用图集工具压缩、去重和生成清单，例如 [PixiJS AssetPack](https://pixijs.io/assetpack/)；输出格式由适配层统一，不因工具名相同就默认兼容。
- 生成和编辑位图时继续遵守当前 imagegen 工作流。自动格式转换与图集构建不应悄悄改变角色外观或素材许可。

## 10. 一千款所需的架构升级

### 10.1 从十款合集到独立游戏包

当前 `apps/codex-stage/arcade.js` 会把所有函数和图片序列化进注入代码。这个方式保留为旧版兼容路径，但不能用它承载一千款。

建议拆成:

1. **可信宿主:** 接收经过脱敏的任务生命周期，管理开始、停止、静音、窗口、输入焦点和本地偏好。
2. **引擎与 SDK:** 生命周期、存档接口、素材解析和测试契约；引擎只加载一份，不给每个包复制完整依赖树。
3. **游戏包:** 经审核的规则实现、关卡、素材清单、输入能力、许可、版本和兼容信息。
4. **目录服务与本地缓存:** 展示与检索目录，下载并验证不可变包，管理收藏和容量上限。
5. **创作与验收工具:** 构建、试玩、截图、回放、性能、许可和安全检查。

游戏包建议包含 `game.json`、规则入口、关卡数据、`assets/`、回放用例、预览、README、LICENSE/NOTICE 和素材来源清单。记录主类、辅助标签、玩法方向、引擎版本、输入需求、离线能力、包体、内容摘要、存档版本和停止契约。

接口必须支持初始化、输入、暂停、恢复、停止、快照和释放。停止和销毁不同: 先同步禁止玩法和音频，再按预算释放资源。不得以保存失败为由继续跑游戏。

### 10.2 下载与运行

- 首装只带精选 10–20 款，后台在空闲期预取少量候选；不在用户开始任务后先下载几十 MB。
- 随机选择同时考虑游戏类型、上次选择、设备能力、是否静音和用户屏蔽项，而不只是对一千个 ID 均匀抽签。
- 本地缓存不足时使用已安装作品，离线照常可玩。收藏作品可固定保留。
- 下载由可信组件完成，只允许经审核的资源地址和摘要，游戏自身不联网。
- 损坏包、版本不兼容或解码失败应降级到本地可用作品，不能拖累任务界面。
- 多任务并行时默认只呈现当前可见任务，并限制活动游戏实例；不要每个工具启动一局。

PixiJS 的资源体系支持清单、后台加载、缓存和卸载，可作为接口设计参考，不代表当前项目已经实现了上述内容。[PixiJS Assets](https://pixijs.com/8.x/guides/components/assets)

### 10.3 安全隔离是前置条件

Shadow DOM 只隔离样式，不是社区代码安全边界。第一阶段只发行经过审核的游戏代码；外部创作者不能把任意 JS 放进 Codex 页面。

P0 验证隔离 iframe/独立运行上下文方案，禁止同源权限、导航、剪贴板、文件、摄像头、麦克风和网络访问。消息使用窄接口、来源校验、大小和频率限制；不把宿主 token、原始任务数据或本机路径传给游戏。iframe 沙箱配置有具体限制，必须结合宿主 CSP 实测。[MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)

仅设置 iframe 不能保证主线程免受死循环影响。对计算和调度建立可终止的执行边界与看门狗，在目标环境验证故障是否能被隔离；未证明之前，不允许不受信任代码运行。发布签名证明来源，不证明代码安全。

如果当前 Codex 版本阻止安全加载，不修改其全局安全设置，不禁用 web security；该版本仅提供本地独立试玩窗口，并明确显示兼容状态。

### 10.4 Speakon 的后续位置

把按键输入和灯光/声音输出定义为可选能力。单键作品能声明 tap、doubleTap、hold 的语义映射；需要二维瞄准的作品不要伪装成无屏幕可玩。

音频单键玩法另设验证集，测试反馈可辨识和真实硬件延迟。游戏按键不能批准邮件、电话或任何 Agent 动作。当前 FinalButton、ActionProof 和既有场景包保持独立。

## 11. 标准制作流程

| 阶段 | 产物 | 放行条件 |
| --- | --- | --- |
| A. 立项与去重 | 一页作品说明、玩法特征、目标人群、关键未知问题 | 和同方向作品有实际区别，有可验证假设 |
| B. 可玩灰盒 | 无昂贵素材的核心规则、输入和短关卡 | 有真实选择，能赢能输，不存在明显挂机或乱按最优解 |
| C. 美术与声音基准 | 关键画面、主体动作小样、音效小样 | 在真实小窗口中成立，而非只看大图 |
| D. 垂直切片 | 一段完整可玩体验，真实镜头、动作、音效与结束流程 | 用户或独立评审愿意让它成为后续质量基准 |
| E. 内容扩展 | 经设计的关卡/遭遇/组合，难度和变体 | 不依赖提高速度或换颜色，保留作品核心 |
| F. 自动验证 | 回放、通关/失败、输入、停止、性能、安全、来源报告 | 硬门槛全部通过，报告对应当前构建 |
| G. 独立试玩 | 观察记录、问题分级、修复与复测 | 没有关键理解/操作障碍，亮点在试玩中可感知 |
| H. 发布 | 包摘要、预览、版本、回滚和贡献说明 | 构建可复现，资源完整，已批准而非仅生成完成 |

每批同时推进少量作品，设计、规则实现、美术、声音和 QA 可以分角色协作，但每款只有一个负责人维护完整意图。共享代码由少数维护者审查，避免多个工作单元同时改公共引擎。

技能来源中的组合筛选方法有价值，但本项目不照搬所有默认做法。例如原型可能建议 CDN 或外部调试依赖，正式游戏运行时必须改为受控本地资源。

## 12. 测试与性能预算

以下是 P0 待校准的目标，不是现有性能实测结果:

| 项目 | 初始目标 |
| --- | --- |
| 视口 | 约 590px Dock、390px 窄窗口、桌面试玩；DPR 1/2 |
| 帧率 | 基准设备目标 60 FPS；较弱设备降级到稳定 30 FPS，减少特效而非改物理速度 |
| 帧耗时 | 60 FPS 配置 p95 总帧耗时目标低于 16.7ms，单独测长帧与主线程占用 |
| 输入反馈 | 基准环境输入到可见反馈 p95 目标不超过 50ms |
| 任务完成 | 收到事件后立即拒绝输入和关闭声音；下一次可呈现帧不再推进模拟，不人为排队延迟 |
| 已缓存启动 | 基准环境首个可操作画面目标小于 1 秒 |
| 包体 | 普通作品目标不超过 8 MB；较重作品需解释价值并单独批准 |
| 内存 | 初始目标单活动实例 JS+纹理增量约 100 MB 内；实测不达标则收缩纹理与效果 |
| 回归 | 连续切换 100 次、启动/停止 100 次、前后台切换、音频中断和资源加载失败 |

需要用 Mac M5 32 GB 和至少一台较低配置设备测量。浏览器 CPU 降速可帮助发现问题，但不能代替另一台真实设备的 GPU、输入和功耗测试。运行游戏时还应检查是否明显影响 Codex 输入、滚动和任务执行。

测试分层:

- 规则层: 碰撞、资源消耗、胜败、重复输入、状态边界、保存恢复；玩法随机数使用固定 seed。
- 可玩性层: 编写合法操作回放证明精选关卡可完成；对竞技/无尽玩法验证目标行为与多策略表现，不假定它们都有通关结局。
- 反策略退化: 比较不操作、一直按、盲目随机与有意图策略，排查形式上可玩但实际上不需要参与的设计。
- 浏览器层: Playwright 真实指针/键盘/触控操作，像素、截图、音频调度、控制台和资源错误检查。[Playwright](https://playwright.dev/docs/intro)
- 视觉层: 待机、关键动作、危险密集、成功、失败、暂停、停止截图；多尺度和减少动效模式，不能只看 DOM 是否存在。
- 集成层: 重复/乱序/无关任务事件、多个任务、宿主刷新、游戏加载中任务结束、停止后音频尚未解码完成等竞态。
- 兼容层: 正式 Codex 宿主实测和独立浏览器测试分别记录。模拟 Shadow DOM 测试不等于实际 Codex 版本兼容。
- 安全层: 非白名单网络、路径穿越、压缩包炸弹、超大图片、过量音频/粒子、恶意消息、敏感信息泄漏和权限探测。

不能要求跨浏览器的浮点物理永远逐位一致。回放优先锁引擎版本和环境，必要时验证容差/状态不变量，而不是用脆弱的逐像素相等替代规则证明。

## 13. 分阶段交付

| 阶段 | 累计正式作品 | 主要交付 | 进入下一阶段的条件 |
| --- | ---: | --- | --- |
| P0 生产基础 | 维持现有 10 款 | 引擎对比、包接口、安全加载试验、生命周期适配、来源锁定、预算基线 | 不降低现有兼容与停止语义；在真实宿主验证，不安全则停在独立窗口 |
| P1 标杆切片 | 先挑 6 款候选，不为数量发布 | 覆盖物理、平台、射击、空间谜题、卡牌/战术、调度的完整体验 | 确定真正被认可的画面与手感；旧作品重制也可成为候选 |
| P2 类别验证 | 20 款 | 每制作大类至少一款，建立不同品类的验收样例 | 20 类都能适应小窗和中断，失败类别调整配额 |
| P3 玩法覆盖 | 100 款 | 每个已验证玩法方向一款，正式目录、创作者样例与贡献 CI | 去重与试玩结果证明多样性；依据成本和效果重排计划 |
| P4 流程扩展 | 300 款 | 每方向约三款，开放受审查贡献，检验重用是否变成同质化 | 批量制作质量不下降，安全审核和返工能力跟得上 |
| P5 完整目录 | 1,000 款 | 逐批扩展，成熟方向最多十款，精选合集与长期维护 | 每款单独通过，没达标的保留空位或重分配，不降标准凑数 |

P1 的六个切片不是承诺再加六个独立游戏，也不要求推翻当前十款。优先从可复用基础里挑选，拿最小成本建立新的质量上限。

生产期以小批次推进，每批建议 5–10 款。素材、构建和测试可并行，入库审查独立进行。一个模板出现共性缺陷时停止扩散，修模板并重测受影响作品。

不在缺少制作数据时承诺“一千款几天完成”。前 20 款记录每阶段耗时、生成次数、返工率、包体、外部费用和人工试玩需求，再给出后续排期及预算区间。

本次提案不创建定时任务、不启动长期无人值守生成、不使用付费账户，也不把“不怕 token”当作购买或无限调用外部服务的授权。

## 14. 体积与发布

现有实测基线: 十款游戏相关文件约 6.4 MB，图片原件约 2.6 MB，内嵌 Base64 图片约 3.5 MB。两份素材并存不适合作为一千款的长期布局。

按每款新增成品代码与素材平均 2–8 MB 规划，一千款完整内容库约 **2–8 GB**，共享引擎另计。原始模型、工程文件、未采用的生成结果、多版本历史和测试视频另存，不能把这一估算当成全部制作数据的总量。

- 主 Git 仓库存规则、SDK、清单、测试和少量样例；源码快照可先设 50–200 MB 的预算，实际按试产结果修正。
- 发行素材按包发布到 Releases 或对象存储，通过摘要去重，不把每次压缩产物、Base64 副本和视频录屏提交进 Git。
- 首装目标 50–150 MB，包含精选内容和所需运行组件；用户无需装 Blender、关卡编辑器或素材制作软件。
- 默认缓存设上限，提供查看占用、删除缓存、保留收藏和下载离线合集的功能。
- 二进制历史、多平台构建和备份会增加存储成本，发布前单独估算。CDN 或付费生成服务在采用前确认费用。

## 15. 社区与发现机制

先做“一千款可浏览、可试玩、可贡献的游戏目录”，不急于做带账户的商店。

- 贡献包里有可运行源码、素材来源、输入契约、回放和预览，不仅是一张海报或一段提示词。
- 用每批精选合集和 10–20 秒真实游玩录屏展示特色。预览来自实际游戏，不剪成游戏里不存在的效果。
- 维护新手友好的创作模板，以及一款从灰盒到最终打磨的完整示例；复用验证过的 Skills 和工具链。
- “首批精选”和“社区试验”分开呈现，所有作品都过安全门槛，试验品不自动混入默认随机池。
- 用户可以收藏、屏蔽类别、固定游戏或选择随机，不用成就、通知和连续奖励把人从任务结果拉走。
- 分享只包含游戏画面、游戏 ID/seed 和可选分数，不包含 Agent 对话、文件名称或工作内容。默认不上传使用记录，反馈由用户选择提交。
- 目标是让创作者能做出自己的作品，让用户记住不同游戏；不保证数量本身带来 GitHub stars、传播或硬件销量。

## 16. 下一次实施的明确范围

建议批准后先做 P0 和 P1，不直接生成余下 990 款:

1. 确定并验证引擎、隔离加载、包格式、任务停止和保存接口，保留现有十款回归。
2. 引入经过许可与安全核对的少量 Skills，记录版本；只安装必要的软件。
3. 建立素材制作、动作预览、音效检查、测试截图和发布报告的可重复流程。
4. 做六个风格和操作明显不同的垂直切片，逐个展示和试玩。没有通过的继续打磨或淘汰。
5. 根据真实结果确认类别配额、正式主引擎、单款预算、生产速度和下一批名单。

需要用户做的准备很少: 首选安装 Blender，关卡制作时再准备 LDtk，逐帧工具在 LibreSprite/Aseprite 中二选一。付费工具暂不购买。用户最重要的参与不是替我写游戏，而是帮我们确认哪种完成度真正值得成为一千款的标准。
